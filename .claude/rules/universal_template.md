# 通用项目模板

> 适用于所有新项目的基础规则和文件结构模板。每个新项目开始时复制此目录并按实际情况填充。

## .claude/rules/ 目录结构

```text
.claude/rules/
├── project_rules.md          # 项目长期规则
├── project_framework.md      # 项目框架描述
├── todolist.md               # 待办事项
├── project_iteration_log.md  # 迭代记录
└── universal_template.md     # 本文件（通用模板）
```

## project_rules.md 通用规则模板

```markdown
# 项目长期规则

- 每次开始工作前先阅读 .claude/rules/ 下的所有规则文件。
- 始终保持大局观，优先保证整条业务链路稳定，不只修单点问题。
- 任何修改都必须以"不破坏现有全部功能"为前提，先兼容、后优化。
- 每次完成改动后，必须做真人模拟测试，再结束本轮工作。
- 完成修改并确认功能无误后，默认执行推送部署。
- 每次动手前先更新 todolist.md 与 project_iteration_log.md；完成后再补齐结果。
- 每次改动完成后，更新项目框架、todolist、迭代记录，写清改动、结构变化、遗留事项和下一步。
- 代码保持简洁高效，不要冗余堆叠。优先复用已有工具函数和组件，避免重复造轮子。
- 项目依赖和工具链不得随意更换，新增依赖需确认兼容且无冗余替代品。
- 目标平台和运行环境约束：（按项目填写，如"手机端微信内打开"或"桌面浏览器"）。
- 部署目标和构建配置：（按项目填写，如"GitHub Pages"或"Vercel"）。
```

## 跨项目通用原则

### 工作流
1. 开工前必读 .claude/rules/ 全部文件，结束后更新 todolist/framework/iteration_log。
2. 多步骤任务用 TodoWrite 展示待办并实时更新。
3. 推送部署后必告知 commit hash 前7位 + 部署 URL。
4. 每次改动后整理线上验证清单供用户验收。
5. 验证通过后及时 commit + push，不积压。
6. 每次用 GLM 模型后运行 `python "c:\Users\42151\.glm-tools\glm_usage.py" --all` 查两个 Key 用量并报告。
7. 复杂任务、跨天任务、上下文较长任务在阶段切换时必须做一次会话交接整理，写清当前目标、已确认结论、失败方案、阻塞点和下一步。
8. 长链路任务要设置检查点，确保每个阶段都可恢复、可对比、可回退。

### 编码原则
9. 必须通过 Task/Skill 实际调用已安装的智能体和技能。
10. 新功能→研究现有实现/官方文档/生态方案→编排→编码→自查→验证；Bug→定位根因→最小修复。
11. 代码改动后自动做安全/类型/错误处理自查。
12. 渐进迭代小步快跑，不破坏现有功能，先兼容后优化。
13. 复用已有工具函数和模式，不重复造轮子。
14. 涉及移动端时兼容窄屏、触控、安全区。
15. 构建或类型错误必须按“最小修复、逐错验证”处理：一次只修一类问题，每修一次立即复验，连续失败要回到根因分析。
16. 分析类任务在相互独立时优先并行执行，前后强依赖的实现步骤再串行推进。
17. 需要沉淀新规则或经验时，先判断是否重复、是否属于跨项目能力，再决定写入全局模板、项目规则或迭代记录。

### 质量与验证
18. 任何交付都必须经过显式质量门禁：格式检查、lint/类型检查、相关测试、错误处理与安全复核；未通过不得视为完成。
19. 代码评审与变更审查只报告高置信问题，优先指出会引发功能错误、安全问题、数据风险或明显违背项目约定的项。
20. 发布后必须做最小线上巡检，至少确认版本已更新、核心页面可打开、关键交互可走通、缓存未导致旧包残留。
21. 涉及外部内容、AI 生成内容、用户输入内容时，默认按不可信输入处理，必须做格式清洗、长度约束、显示安全和异常兜底。
22. 性能优化必须可验证，至少记录关键指标、基线或用户可感知收益，避免只凭主观感觉判断“更快了”。
23. 涉及弹窗、表单、分页、播放控件等交互时，要同步检查可访问性：键盘可达、焦点可见、状态可感知、错误提示明确。

### 安全
24. 敏感信息（密码/API Key）不得写入代码或日志，必须加密存储。
25. 涉及用户输入/API/认证时做安全扫描。
26. 自动接受权限、批量执行、自动化 Hook 只能用于目标清晰、边界稳定、风险可控的任务；探索性排查和敏感操作默认不自动放权。
27. 认证状态、前端本地标记、缓存结果都不能直接视为真实权限来源，涉及权限判断时必须回到可信会话、服务端或策略边界验证。
28. 日志输出默认脱敏，避免打印密钥、完整凭证、敏感响应体和不必要的原始数据。

### 规则维护
29. 项目规则只记项目特有内容，通用原则写在此文件，不重不漏。
30. 文档、命令说明、架构说明优先依据代码和配置事实更新，不用过时口述替代真实现状。
