# 通用项目模板

> 适用于所有新项目的基础规则和文件结构模板。每个新项目开始时复制此目录并按实际情况填充。
> 
> 本文件整合了 ECC（Everything Claude Code）项目精华，提炼出可跨项目复用的编码最佳实践。

## .trae/rules/ 目录结构

```
.trae/rules/
├── project_rules.md          # 项目长期规则
├── project_framework.md      # 项目框架描述
├── todolist.md               # 待办事项
├── project_iteration_log.md  # 迭代记录
└── universal_template.md     # 本文件（通用模板）
```

## project_rules.md 通用规则模板

```markdown
# 项目长期规则

> 通用原则见 universal_template.md"跨项目通用原则"，此处仅记录本项目特有规则。

## 项目特有规则
- （按项目填写，只记录本项目独有的规则，不与通用原则重复）

## 防止版本错乱/回退规则
- 禁止整文件重写，必须使用局部搜索替换
- 改动前先确认现有代码状态
- 保持历史修复的完整性
- 小步提交，每个独立修复单独 git commit
- 修复前先查 git log

## 推送部署与测试规则
- 推送部署必须确认成功并告知用户
- 推送后教用户线上测试方法
- 推送后给运行总结
- 优化方案写入 todolist 并实时更新进度
```

## 跨项目通用原则

### 一、项目管理原则

1. **规则先行**：每个项目必须有 .trae/rules/ 目录，开工前先读规则。
2. **文档同步**：每次改动前后都要更新规则文件，保持文档与代码一致。
3. **渐进迭代**：先保证功能正确，再优化体验，最后考虑重构。
4. **兼容优先**：新代码不能破坏已有功能，先兼容后优化。
5. **简洁高效**：代码保持简洁，复用已有能力，不重复造轮子。
6. **真人验证**：每次改动后做真人模拟测试，覆盖实际操作路径。
7. **及时提交**：验证通过后及时 git commit + push，不积压改动。
8. **移动优先**：如项目涉及移动端，任何调整都要兼容窄屏、触控和安全区。
9. **隐私安全**：账号密码、API Key 等敏感信息不得写入代码、配置文件或日志，必须加密存储或使用环境变量。
10. **文件有序**：代码文件放入已有目录的合理位置，不随意在根目录创建新文件；新文件必须符合项目目录结构约定。
11. **防回退**：已完成的优化和拆分不得被后续修改还原，修改文件前必须确认现有代码状态。
12. **部署告知**：推送部署成功后必须告知用户，给测试指引和运行总结。
13. **方案归档**：优化方案必须写入 todolist.md 并实时更新进度，避免后续遗忘。
14. **规则不重不漏**：项目规则和通用规则之间不重复不遗漏，通用规则更新后同步更新记忆。

### 二、编码风格原则（源自 ECC）

15. **不可变优先**：始终创建新对象，不要修改现有对象。用展开运算符 / map / filter 返回新副本，而非原地修改。
16. **KISS**：选择能实际工作的最简方案，避免过早优化，清晰优于巧妙。
17. **DRY**：提取重复逻辑为共享函数或工具，避免复制粘贴导致的实现漂移。只在重复真实存在时才引入抽象。
18. **YAGNI**：不提前构建不需要的功能或抽象，从简单开始，需要时再重构。
19. **文件组织**：多个小文件优于少数大文件。单文件 200-400 行为佳，800 行为上限。按功能/领域组织，而非按类型。
20. **函数精简**：函数不超过 50 行，避免超过 4 层嵌套。优先使用早返回替代深层条件嵌套。
21. **错误处理**：每一层都要显式处理错误，UI 层给用户友好提示，服务端记录详细上下文，绝不静默吞错误。
22. **输入验证**：在系统边界验证所有输入，使用 schema 验证，快速失败并给出明确信息，永远不信任外部数据。

### 三、命名规范（源自 ECC）

23. **变量和函数**：`camelCase`，使用描述性名称，布尔值用 `is` / `has` / `should` / `can` 前缀。
24. **接口、类型、组件**：`PascalCase`。
25. **常量**：`UPPER_SNAKE_CASE`。
26. **自定义 Hook**：`camelCase` 加 `use` 前缀（如 `useDebounce`）。
27. **测试命名**：用描述行为的句子，如"当查询无匹配时返回空数组"。

### 四、安全检查清单（源自 ECC）

28. **提交前安全检查**：
    - 无硬编码密钥（API Key、密码、Token）
    - 所有用户输入已验证
    - SQL 注入防护（参数化查询）
    - XSS 防护（HTML 转义）
    - CSRF 保护已启用
    - 认证/授权已验证
    - 错误信息不泄露敏感数据
29. **密钥管理**：永远不在源码中硬编码密钥，使用环境变量或密钥管理器，启动时验证必需密钥存在，已泄露的密钥立即轮换。
30. **安全响应协议**：发现安全问题 → 立即停止 → 评估 → 修复严重问题 → 轮换已泄露密钥 → 全局排查同类问题。

### 五、代码审查标准（源自 ECC）

31. **审查时机**：代码写完或修改后、提交到共享分支前、涉及安全敏感代码时、架构变更时。
32. **审查严重级别**：
    - **CRITICAL**（阻塞）：安全漏洞或数据丢失风险
    - **HIGH**（警告）：Bug 或重大质量问题
    - **MEDIUM**（建议）：可维护性问题
    - **LOW**（备注）：风格或微小建议
33. **审查清单**：代码可读且命名合理、函数精简（<50行）、文件聚焦（<800行）、无深层嵌套（>4层）、错误显式处理、无硬编码值、测试覆盖新功能。

### 六、测试要求（源自 ECC）

34. **覆盖率目标**：最低 80%。
35. **测试类型**：单元测试（函数/工具/组件）、集成测试（API/数据库操作）、E2E 测试（关键用户流程），三种都必需。
36. **TDD 工作流**：先写测试（RED）→ 写最小实现（GREEN）→ 重构（IMPROVE）→ 验证覆盖率。
37. **必须测试的边界情况**：null/undefined 输入、空数组/字符串、无效类型、边界值、错误路径、竞态条件、大数据量、特殊字符。
38. **测试反模式**：不测实现细节（测行为）、测试间不共享状态、断言要具体有意义、外部依赖必须 mock。

### 七、架构模式（源自 ECC）

39. **Repository 模式**：将数据访问封装在统一接口后（findAll / findById / create / update / delete），业务逻辑依赖抽象接口而非存储机制。
40. **API 响应格式**：统一信封结构——成功标识、数据载荷、错误信息、分页元数据。
41. **组件组合优于继承**：用组合模式构建组件，用 compound components 共享状态，用 render props 处理可变标记。
42. **状态管理分层**：服务端状态用 SWR/React Query、客户端状态用 Zustand/Jotai、URL 状态用 search params、表单状态用 React Hook Form。不将服务端状态重复存入客户端 store。
43. **URL 即状态**：可共享状态持久化到 URL——筛选、排序、分页、当前标签页、搜索词。

### 八、前端模式（源自 ECC）

44. **组件拆分**：容器组件负责数据加载和副作用，展示组件只接收 props 并渲染 UI，展示组件保持纯函数。
45. **数据获取**：优先并行加载独立数据，避免父子请求瀑布流，使用 stale-while-revalidate 缓存策略。
46. **乐观更新**：快照当前状态 → 应用乐观更新 → 失败时回滚 → 回滚时给出可见错误反馈。
47. **代码质量完成检查**：
    - 代码可读且命名合理
    - 函数精简（<50行）、文件聚焦（<800行）
    - 无深层嵌套（>4层）
    - 错误已显式处理
    - 无硬编码值（使用常量或配置）
    - 使用不可变模式

### 九、Git 工作流（源自 ECC）

48. **提交格式**：`<type>: <description>`。类型：feat、fix、refactor、docs、test、chore、perf、ci。
49. **PR 工作流**：分析完整提交历史（不仅是最新提交）→ 起草全面的 PR 摘要 → 包含测试计划 → 新分支用 `-u` 推送。

### 十、Web 设计质量标准（源自 ECC web/design-quality.md）

54. **反模板设计**：不输出千篇一律的模板 UI。每个有意义的前端界面应至少体现以下 4 项：层级对比｜间距节奏感｜深度/层叠｜有性格的字体搭配｜语义化用色｜精心设计的交互状态｜破格编辑式布局｜纹理/氛围｜动效澄清流程｜数据可视化融入设计系统。
55. **禁止的默认模式**：统一卡片网格无层级｜标准 hero 区域（居中标题+渐变光斑+通用按钮）｜未修改的库默认样式｜扁平无层次布局｜统一圆角/间距/阴影｜安全灰白+一个装饰色｜千篇一律的仪表盘布局｜默认字体栈。
56. **写前端代码前**：先确定具体风格方向（编辑/杂志、新粗野、玻璃态、暗色奢华、Bento 布局、滚动叙事、3D 融合、瑞士国际、复古未来等），再定义调色板和字体搭配，收集真实参考。

### 十一、Web 性能标准（源自 ECC web/performance.md）

57. **Core Web Vitals 目标**：LCP < 2.5s / INP < 200ms / CLS < 0.1 / FCP < 1.5s / TBT < 200ms。
58. **Bundle 预算**：落地页 JS < 150kb(gzip) / CSS < 30kb；应用页 JS < 300kb / CSS < 50kb；微站 JS < 80kb / CSS < 15kb。
59. **加载策略**：内联关键 CSS → preload hero 图片和主字体 → defer 非关键 CSS/JS → 动态 import 重型库。
60. **图片优化**：明确 width/height → hero 用 loading=eager + fetchpriority=high → 其余 lazy → 优先 AVIF/WebP → 不超过渲染尺寸。
61. **字体加载**：最多 2 个字体族 → font-display: swap → 子集化 → 只 preload 关键 weight/style。
62. **动效性能**：只动画合成友好属性（transform/opacity/clip-path）→ 窄范围使用 will-change 并及时移除 → 简单过渡用 CSS → JS 动画用 requestAnimationFrame → 避免 scroll 事件节流，用 IntersectionObserver。

### 十二、Web 安全标准（源自 ECC web/security.md）

63. **CSP 配置**：生产环境必须配置 Content-Security-Policy，script 用 nonce 而非 unsafe-inline。
64. **XSS 防护**：不注入未转义 HTML → 避免 innerHTML/dangerouslySetInnerHTML → 转义动态模板值 → 必要时用 vetted sanitizer。
65. **第三方脚本**：异步加载 → CDN 用 SRI → 季度审计 → 关键依赖优先自托管。
66. **HTTPS 和安全头**：HSTS(max-age=31536000;includeSubDomains;preload) / X-Content-Type-Options:nosniff / X-Frame-Options:DENY / Referrer-Policy:strict-origin / Permissions-Policy:camera=(),microphone=(),geolocation=()。
67. **表单安全**：状态变更表单启用 CSRF → 提交端点限流 → 客户端+服务端双重验证 → 优先 honeypot 而非重型 CAPTCHA。

### 十三、Web 测试标准（源自 ECC web/testing.md）

68. **测试优先级**：视觉回归（关键断点截图）→ 无障碍（键盘/对比度/reduced-motion）→ 性能（Lighthouse）→ 跨浏览器（Chrome/Firefox/Safari）→ 响应式（320/375/768/1024/1440/1920）。
69. **E2E 要点**：避免基于超时的断言 → 用确定性等待 → 视觉组件用视觉回归而非脆弱标记断言。

### 十四、Web 编码风格（源自 ECC web/coding-style.md）

70. **文件组织**：按功能/页面区域组织，不按文件类型（hero/、scrolly-section/、ui/）。
71. **CSS 变量作为 Design Token**：不硬编码调色板/字体/间距，用 CSS 自定义属性（:root 定义 → clamp() 响应式）。
72. **语义 HTML 优先**：header/nav/main/article/section/footer → ARIA 标签 → 焦点管理。

### 十五、Token 优化策略（源自 ECC docs/token-optimization.md）

73. **模型选择**：日常编码用 Sonnet → 复杂架构用 Opus → 简单查找用 Haiku。
74. **上下文管理**：不相关任务间清上下文 → 逻辑断点处压缩 → 子 agent 做探索避免主上下文膨胀。
75. **压缩时机**：探索后/实现前 ✅ 里程碑后 ✅ 调试后/继续新工作前 ✅ 上下文大切换前 ✅ ｜ 实现中间 ❌ 调试活跃问题时 ❌ 多文件重构中 ❌。

### 十六、TodoWrite 最佳实践（源自 ECC rules/common/hooks.md）

76. **Todo 写法**：多步骤任务必须用 TodoWrite 跟踪 → 验证对指令的理解 → 实时调整方向 → 展示细粒度实施步骤。
77. **Todo 暴露的问题**：步骤乱序 → 遗漏项 → 多余项 → 粒度不对 → 需求理解偏差。

### 十七、开发工作流（源自 ECC）

50. **Plan Before Execute**：复杂功能先用 TodoWrite 做规划，识别依赖和风险，分阶段实施。
51. **验证循环**：完成改动后执行完整验证——构建 → 类型检查 → lint → 测试 → 安全扫描 → diff 审查。
52. **性能意识**：避免在上下文窗口后 20% 做大规模重构或跨文件功能实现；单文件编辑、文档更新等低敏感度任务可适当放松。
53. **知识捕获**：个人调试笔记和偏好 → 写入记忆；团队/项目知识（架构决策、API 变更）→ 写入项目文档结构；如果当前任务已产出相关文档或代码注释，不重复写。

### 十八、架构设计原则（源自 ECC architect agent）

81. **关注点分离**：单一职责、高内聚低耦合、组件间清晰接口、独立可部署。
82. **可扩展性**：水平扩展能力、无状态设计、高效查询、缓存策略。
83. **可维护性**：清晰组织、一致模式、完善文档、易于测试。
84. **架构反模式预警**：大泥球（无清晰结构）、万能锤（同一方案解所有问题）、过早优化、紧耦合、上帝对象（一个类/组件包办一切）。
85. **架构决策记录（ADR）**：重要架构决策需记录——上下文、决策、后果（正面+负面）、考虑过的替代方案。

### 十九、搜索优先原则（源自 ECC search-first skill）

86. **先搜后写**：写新功能前先搜索——代码库中是否已有？npm/PyPI 是否有现成库？是否有 MCP 工具可用？GitHub 是否有成熟实现？
87. **决策矩阵**：完全匹配且维护良好 → 直接采用；部分匹配 → 扩展封装；多个弱匹配 → 组合使用；无合适方案 → 基于研究结果自己构建。

### 二十、代码简化原则（源自 ECC code-simplifier agent）

88. **清晰优于巧妙**：保持与仓库风格一致、保留行为不变、只在结果明显更易维护时才简化。
89. **简化目标**：提取深层嵌套为命名函数、用早返回替代复杂条件、用 async/await 简化回调、移除死代码和未使用 import、合并重复逻辑。

### 二十一、重构清理原则（源自 ECC refactor-cleaner agent）

90. **安全重构流程**：先用检测工具（knip/depcheck/ts-prune）分析 → 按风险分类（安全/谨慎/危险）→ 逐类删除（依赖→导出→文件→重复）→ 每批后跑测试 → 每批后提交。
91. **重构禁忌**：不要在功能开发期间重构、不要在部署前重构、没有测试覆盖不要重构、不理解代码不要删。

### 二十二、上下文管理（源自 ECC strategic-compact/context-budget skills）

92. **战略压缩**：在逻辑边界处手动整理上下文——探索后/规划前、里程碑完成后、切换不相关任务时；不要在实现过程中间整理。
93. **长会话策略**：紧密耦合的单元在同一会话完成；重大阶段转换后开新会话；里程碑完成后整理，而非调试中间。
94. **15 分钟单元规则**：每个工作单元应独立可验证、有单一主要风险、有清晰的完成条件。

### 二十三、Santa Method 双重验证（源自 ECC santa-method skill）

95. **关键输出双重验证**：面向用户的发布内容、部署代码、合规性内容，使用两个独立审查者（不同上下文）同时审查，两者都通过才能发布。
96. **收敛循环**：发现问题 → 修复所有问题 → 重新提交两个审查者 → 循环直到收敛；设最大迭代次数，超限则升级。

### 二十四、无障碍设计（源自 ECC a11y-architect agent）

97. **WCAG 2.2 核心要求**：可感知（文本替代、对比度、自适应）、可操作（键盘可达、焦点可见、触控目标 ≥24x24px）、可理解（一致性、输入辅助）、健壮（辅助技术兼容）。
98. **无障碍反模式**："点击这里"链接、固定尺寸容器、键盘陷阱、自动播放媒体、无标签的图标按钮。

### 二十五、API 设计规范（源自 ECC api-design skill）

99. **RESTful URL 规范**：资源用名词复数、kebab-case、查询参数用于过滤/排序/分页。
100. **HTTP 状态码语义使用**：200 获取成功、201 创建成功、204 删除成功（无返回体）、400 验证失败、401 未认证、403 无权限、404 不存在、409 冲突、429 限流、500 服务器错误。
101. **统一响应格式**：成功——data + meta（分页）+ links；错误——error.code + error.message，永远不暴露内部细节。

### 二十六、后端模式（源自 ECC backend-patterns skill）

102. **服务层分离**：数据访问（Repository）→ 业务逻辑（Service）→ 请求处理（Controller/Middleware），各层职责清晰。
103. **N+1 查询预防**：避免循环内单条查询，改为批量获取后用 Map 映射。
104. **中间件管道**：认证 → 授权 → 日志 → 限流 → 业务处理，每层只做一件事。

### 二十七、Agent 工程原则（源自 ECC agentic-engineering/ai-first-engineering skills）

105. **Eval-First 循环**：定义能力评估和回归评估 → 运行基线 → 执行实现 → 重新评估并比较差异。
106. **AI 生成代码审查重点**：不变量和边界条件、错误边界、安全和认证假设、隐藏耦合和发布风险；不在已自动化格式/lint 的风格上浪费时间。
107. **成本纪律**：每个任务追踪——模型、token 估算、重试次数、耗时、成功/失败；仅在低级模型因推理能力不足失败时才升级。
