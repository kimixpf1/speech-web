## 项目特有规则

- 始终保持大局观，优先保证整条业务链路稳定，不只修单点问题。
- 管理员测试账号：admin / kimiclaw1（保护好数据安全）。
- 涉及新增文章、AI 提取、摘要、解读、详情展示、删除链路时，要联动检查上下游是否一起正常。
- 发现线上现象与本地修复不一致时，优先排查是否未推送、未部署、缓存未刷新或旧数据未清洗。
- 在优化新功能时，必须同步关注旧数据兼容、缓存兼容和数据库持久化兼容。
- 推送部署前先本地脚本构建 + 模拟真人测试，确认无误后再推送。
- 推送部署后必须进行线上平台真人模拟测试，验证线上效果与本地一致。

## 防止版本错乱/回退规则（2026-04-08 永久写入）

**根因**：AI 编码会话在修改文件时，有时会整文件重写而非局部编辑，导致该文件中之前已提交的修复被静默覆盖丢失。多次会话累积后，多个已修复的 bug 会同时回归。

**核心原则：每个文件都是脆弱的，一次整文件重写就可能丢失之前所有修复。**

1. **禁止整文件重写**：修改文件时必须使用局部搜索替换（Search/Replace），绝不能将整个文件内容全部覆盖。除非文件本身需要从头重写且用户明确同意。
2. **改动前先确认现有代码状态**：每次修改某个 bug 前，先用 grep/搜索确认该位置是否已经有修复代码存在。如果已存在，先理解为什么还有问题，而不是直接覆盖。
3. **保持历史修复的完整性**：在修复新问题时，必须通读即将修改区域的上下文（至少前后 20 行），确认不会意外删除或覆盖邻近的其他修复代码。
4. **小步提交**：每个独立修复应单独 git commit，不要把多个不相关的修复塞进同一次提交。这样即使某次改动出问题，也能精确回退。
5. **修复前先查 git log**：如果用户报告某个 bug "之前修过"，先用 `git log --oneline --all --grep="关键词"` 搜索相关提交，再用 `git show <hash>` 查看具体改动内容，确保理解之前的修复方案后再决定是否重新应用。
6. **会话延续时必须检查**：每次新会话接手项目时，先用 `git log --oneline -20` 查看最近提交历史，确认代码当前状态与预期一致，发现异常立即修正。
7. **举一反三**：每次发现已完成的优化被回退或功能异常时，必须分析根因并记录到迭代日志，确保同类问题不在其他地方重复发生。

## 推送部署与测试规则（2026-04-11 永久写入）

1. **推送部署必须确认成功**：本地模拟测试通过后，必须确保 git push 成功推送到远端，并告知用户推送内容和部署状态。用户去线上测试时必须能看到最新版本。
2. **推送后教用户测试**：每次推送部署成功后，必须给用户提供线上测试指引（访问哪个URL、点哪个按钮、预期看到什么效果），让用户能独立验证。
3. **推送后给运行总结**：每次推送部署成功后，必须给用户一个本次运行的总结说明，包括：改了什么文件、做了什么优化、解决了什么问题、线上怎么验证。
4. **优化方案写入todolist**：每次生成优化方案后，必须把完整方案写入 todolist.md，包含优化项、涉及文件、预期效果、当前状态，避免后续遗忘或穿插其他修复后需要重新读取代码。
5. **优化进度实时更新**：优化执行过程中实时更新 todolist.md 中的状态（⬜待开始→🔄进行中→✅已完成/⏭跳过），用户可能选择跳过某些优化项，如实记录。
