# 项目长期规则

> 通用原则（规则先行、文档同步、渐进迭代、兼容优先、简洁高效、真人验证、及时提交、移动优先、隐私安全、文件有序、防回退、部署告知、方案归档、规则不重不漏）见 universal_template.md“跨项目通用原则”，此处只保留本项目长期有效、跨轮次复用的规则。

## 本文件职责
- 只记录长期规则、稳定边界、事故级安全网
- 不记录一次性方案、本轮进度、临时排查过程
- 本轮任务、状态、验证结果写入 todolist.md 与 project_iteration_log.md

## 项目特有长期规则
- 始终保持大局观，优先保证整条业务链路稳定，不只修单点问题。
- 管理员测试账号：admin / kimiclaw1；仅用于必要测试，注意数据安全。
- 涉及新增文章、AI 提取、摘要、解读、详情展示、删除链路时，要联动检查上下游是否一起正常。
- 发现线上现象与本地修复不一致时，优先排查是否未推送、未部署、缓存未刷新或旧数据未清洗。
- 在优化新功能时，必须同步关注旧数据兼容、缓存兼容和数据库持久化兼容。
- 推送部署前先本地构建并做真人模拟测试，确认无误后再推送。
- 推送部署后必须进行线上平台真人模拟测试，验证线上效果与本地一致。

## 每轮执行边界
### 开始前必做
1. 通读 .trae/rules/ 下全部规则文件。
2. 在 todolist.md 写明本轮目标、待办、风险点。
3. 在 project_iteration_log.md 新开本轮记录，写清本次目标。

### 进行中必做
1. 优先小步修改，避免把不相关问题混在同一轮处理。
2. 涉及结构或链路变化时，同步回写 project_framework.md。
3. 发现回退、覆盖、线上异常时，先查现状与历史记录，再继续修改。

### 结束前必做
1. 回写 todolist.md：已完成、验证结果、下一步。
2. 回写 project_iteration_log.md：实际改动、验证结果、遗留事项。
3. 若结构或职责变化，回写 project_framework.md。
4. 若涉及代码改动，必须补做 build、lint、真人模拟测试；未通过不得推送。

## 防止版本错乱/回退规则（2026-04-08 永久写入）

**根因**：AI 编码会话在修改文件时，有时会整文件重写而非局部编辑，导致该文件中之前已提交的修复被静默覆盖丢失。多次会话累积后，多个已修复的 bug 会同时回归。

**核心原则：每个文件都是脆弱的，一次整文件重写就可能丢失之前所有修复。**

1. **禁止整文件重写**：修改文件时必须使用局部搜索替换，绝不能将整个文件内容全部覆盖。除非文件本身需要从头重写且用户明确同意。
2. **改动前先确认现有代码状态**：每次修改某个 bug 前，先用搜索确认该位置是否已经有修复代码存在。如果已存在，先理解为什么还有问题，而不是直接覆盖。
3. **保持历史修复的完整性**：在修复新问题时，必须通读即将修改区域的上下文，确认不会意外删除或覆盖邻近的其他修复代码。
4. **小步提交**：每个独立修复应单独 git commit，不要把多个不相关的修复塞进同一次提交。
5. **修复前先查 git log**：如果用户报告某个 bug“之前修过”，先查相关提交，再决定是否重新应用。
6. **会话延续时必须检查**：每次新会话接手项目时，先查看最近提交历史，确认代码当前状态与预期一致，发现异常立即修正。
7. **举一反三**：每次发现已完成的优化被回退或功能异常时，必须分析根因并记录到迭代日志，确保同类问题不在其他地方重复发生。

## 推送部署与测试规则（2026-04-11 永久写入）
1. **推送部署必须确认成功**：本地模拟测试通过后，必须确保 git push 成功推送到远端，并告知用户推送内容和部署状态。
2. **推送后教用户测试**：每次推送部署成功后，必须给用户提供线上测试指引，让用户能独立验证。
3. **推送后给运行总结**：每次推送部署成功后，必须给用户一个本次运行的总结说明，包括改了什么文件、做了什么优化、解决了什么问题、线上怎么验证。
4. **优化方案写入 todolist**：每次生成优化方案后，必须把完整方案写入 todolist.md，包含优化项、涉及文件、预期效果、当前状态。
5. **优化进度实时更新**：优化执行过程中实时更新 todolist.md 中的状态，用户若选择跳过某些优化项，也要如实记录。

## 代码安全网规则（2026-04-12 永久写入）
### 规则 A：import 完整性保护
1. 每次修改某个文件后，必须检查该文件中所有使用的变量、组件、函数是否都有对应 import。
2. 对文件做结构性重构前，先记录当前 import 清单，重构后逐一对照确认。
3. 新增引用时立即补 import，不能拖到最后再统一处理。
4. build 是最终安全网；build 失败则绝对不能推送。

### 规则 B：ErrorBoundary 路径安全
1. 本项目使用 HashRouter + GitHub Pages 子路径部署，任何硬编码跳转都必须使用 /speech-web/#/路径 格式。
2. 禁止使用 / 作为跳转目标。
3. ErrorBoundary 是最后的自救入口，每次改动相关路由都必须验证其返回首页路径正确。
4. 涉及路由跳转时，必须全局检查 window.location.href 与 window.location.replace 的硬编码路径。

### 规则 C：git push 真实性验证
1. push 后不能只看 exit code，必须再验证远端状态。
2. 若 push 后仍显示 ahead，说明未成功，必须重试并再次验证。
3. 用户反馈“还是不行”时，先确认远端是否已经收到最新提交。
